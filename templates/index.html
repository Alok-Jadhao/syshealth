How to read this page

SysHealth answers one question: which instance size has enough memory for your app? Every ? and every underlined label on the page explains the part next to it.

  1. The measure. Each machine reports how much of the time its programs spend waiting for memory, not how full its memory is. A full machine can be fine; a machine whose programs wait is slow. Lower is better.
  2. Three states. Healthy under 10%: enough memory. Degraded 10–40%: noticeably slower. Critical 40% or more: thrashing, and the kernel may start killing programs.
  3. Current state shows every machine as it is now, one card each, from the smallest size to the biggest, with how full its memory is under the reading.
  4. The chart shows the same reading over time. Range picks how far back; Instance picks one machine to look at closely; Show switches to memory in use, to see a full machine that is still fine.
  5. Load test, top right, puts the same memory load on every machine at once, so you can watch the small ones struggle first. Show all three states fills in a test that shows all three at the same moment; Plan it from your users works one out from how many people use your app.
  6. Which size to choose appears under the test form once a test has run: the cheapest size that held your app with room to spare, and what it costs.

        What the number means
        
            
          
            
            The number is the share of time programs on the machine were held up
            waiting for memory. The Linux kernel measures it directly
            (PSI). It is not how
            full memory is. A machine can be 90% full and fine. What matters is
            whether programs have to wait. 20% means that out of every 10 seconds,
            2 were lost waiting, so the work could have run about 20% faster with
            enough memory.
          
            
          
              
          
              
            A state changes only after it has held for 15 seconds, so one spike is
            not reported as a failure. The thresholds come from systems that act on
            this measurement in production: Android’s low-memory killer,
            systemd-oomd and Meta’s oomd. Sources are in
            docs/thresholds.md.
